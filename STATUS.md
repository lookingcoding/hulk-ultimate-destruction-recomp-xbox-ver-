# Hulk Recompiled - work in progress

This is a native Windows port project for the original Xbox version of The Incredible Hulk: Ultimate Destruction. It is an experimental playable build validated through the opening junkyard tutorial, not yet a verified full-campaign port.

Verified input:

- Disc: your own retail disc image of the game (`.iso`, any file name) in `assets/`.
- XDK 5849: XAPILIB, XBOXKRNL, LIBCMT, D3D8, XGRAPHC, DSOUND.
- SDK: TGP482/XboxXBE-Recomp, base commit `0fd00442660573dc342b41c11c6574318f0e8698`, pinned as `sdk/` submodule with the local patches under `patches/` applied by the build script.
- LLVM 23.1.4 portable compiler archive verified against GitHub's SHA256 digest.
- All 26 disc files extracted; streamed data copies SHA256 verified and the complete path/size manifest checked.

Paths:

- Project and local game data: `D:\Projects\Active\Hulk Recompiled`.
- Build, dependency downloads, logs, generated C++: `D:\Projects\Build Cache\Hulk Recompiled`.
- Standalone local install: `D:\Games\Standalone\Hulk Recompiled`.
- Portable compiler: `D:\Projects\Build Cache\Tools\clang+llvm-23.1.4-x86_64-pc-windows-msvc`.
- `generated/` is a junction to the build cache, and the build's `assets/` is a junction to the project's assets.

Static code generation and native executable/DLL compilation succeeded. The final generator reports 46,341 discovered function entries and also reports unsupported instruction decodes; some discovered entries may be data misidentified as code. Successful compilation does not demonstrate that every executable path has been recovered correctly.

The two missing Bink video helpers (`BinkWait` at `0x00367400`, `BinkNextFrame` at `0x00368C90`) and the XDK 5849 dynamic vertex-buffer synchronization helper (`D3D_BlockOnNonSurfaceResource` at `0x0038B130`) were traced and mapped; see reports/symbol-notes.md. The missed thread-notification callback at `0x0034F465` was added to the discovered entry points.

Runtime and SDK fixes:

- `src/game/fibers.cpp`: Xbox SwitchToFiber at `0x00350EBD` needs to switch the native C++ continuation as well as guest ESP. It now bridges to Windows fibers, reproduces the guest nonvolatile-register/SEH save frame, and releases native stacks when the guest deletes a fiber.
- `patches/optical-volume.patch`: CdRom0 retains optical-drive metadata with extracted data too. Volume queries return 2048-byte DVD sectors and zero writable/free space, while HDD sectors remain 512 bytes. The game checks DVD sector size at `0x00088411`; that check remains in place.
- `patches/vtable-discovery.patch`: read-only virtual-method pointers after short/near tail jumps are established before speculative decoding. The first punch exposed a missing method at `0x0001D570`; the patched generator now includes it. See reports/vtable-notes.md.
- `config/game.toml` (`D3D_BlockOnNonSurfaceResource = "0x0038B130"`): maps XDK 5849's vertex-buffer wait helper so dynamic vertex buffers are not overwritten before the D3D12 renderer consumes them, resolving overlapping menu text.
- `patches/audio-prebuffer.patch`: prebuffers 30 ms of audio frames before starting the XAudio2 source voice and raises the audio worker thread priority.
- `patches/z-kernel-io.patch`: implements the six Xbox kernel exports imported by this title that were absent from the pinned SDK (`NtCreateIoCompletion`, `NtSetIoCompletion`, `NtRemoveIoCompletion`, `ObOpenObjectByName`, `NtUserIoApcDispatcher`, `IoQueryVolumeInformation`). Boot now reports `boot: kernel imports resolved, 0 missing`. See reports/kernel-io-notes.md.
- `patches/zz-file-view.patch`: adds `GameInfo::file`, through which the game code can change what the game reads of a file without touching it on disk. `src/common/display_menu.cpp` uses it to serve `misc.rcf` with edited `frontend\fe_real.txt` and `frontend\fe_run.txt` (a Display Options row in the main and pause Options screens, opening a screen of text selectors) and string tables, all placed past the archive's end with the directory pointing at them. The selectors' callbacks are registered beside the game's own (`0x000C4500`) and share the PS2/GameCube-only `AudioQualityChanged` handler (`0x000BBEC0`), told apart by their owners; an `OnHighlight` function sharing the unused `Print` handler (`0x000B46B0`) sets each selector to the current setting as the game does for its own screens (`src/game/hooks.cpp`). Verified in game: both screens render with the game's own art, show the current settings, and changes apply and save to `settings.toml`.
- Host-only changes relink the game DLL, preventing an unnecessary full first-launch rebuild caused by the SDK's executable/DLL freshness check.
- The game's guarded call (`0x32DC20`, `0x2B9850`; USA `0x2152F0`, `0x2D6F10`) installs a `VC20` frame with `esp` and its own return address (`0x343534`) and, when the callback raises, the stub `0x3435B0` restores `esp` and jumps to that address in the middle of the calling function. `patches/zzz-guarded-call-continuations.patch` finds every caller of a `VC20` frame installer and makes the resumed address a function entry **and** an `X86Continuation`; `src/game/hooks.cpp` wraps both guarded calls, so the jump throws `X86Resume` and the frame that owns the resume point catches it and continues there, unwinding the host frames of the callback the way the console's longjmp does. Without that, an entry alone resumed by calling the continuation and then returned into the unwinder, which used its result (1) as a frame pointer and faulted reading `0x11` (`logs/hulk_020.log`).
- The game's frame swap (`0x21F300`, USA `0x31B190`) waits until two vertical blanks have passed since the last swap, its 30 fps gameplay limit, or one while loading (byte `0x4F8024`, USA `0x5554A0`; blanks counted at `0x4F8020`, USA `0x55549C`), which is why the Frame Rate Limit setting did nothing above 30. The simulation steps by measured time clamped to a maximum (`0x86430`), not a fixed step. `src/game/hooks.cpp` tells the swap the blanks have passed, so `app::Pace` is the only limit. Measured in the scripted tutorial on the 11-02 build: caps of 60, 120 and 144 hold about 60, 120 and 138 fps, unlimited about 140-190, all with zero logged errors. The 30 and 60 fps runs match frame for frame early on, so speed is right at 60. Later frames of a scripted run scatter even between two runs at the same cap, so that test cannot judge behaviour above 60 (120, 144 and unlimited did not visibly run fast). The USA change is checked by disassembly (the same instructions as the European wrapper) and has not been run here, for lack of a USA disc. No frame rate above 30 has been played through a real mission yet.
- The bloom pass (`0x226720`, USA `0x325110`) never sets the texture coordinate index and could inherit stage 1 reading set 0 from the scene, which sampled the 640x480 scene with the 160x120 bloom coordinates: flashes of an enlarged top-left quarter under a correctly sized bloom in Lightning Strike. `src/game/hooks.cpp` gives the pass each stage's own coordinates and restores the scene's values after it. Confirmed fixed by playtest on a European disc; the USA change has not been run.
- Field of View and Render Distance (`src/common/view.cpp`, hooks in `src/game/hooks.cpp`, rows 6 and 7 of Display Options, `settings.toml` `fov_increase` and `render_distance`). The render manager (`[0x4E445C]`, USA `[0x4E231C]`) keeps the game's camera (fov +0x5C, aspect, near, far +0x68) and hands it to its render layer (`0x1C2940`, USA `0x1C1F30`) when byte +0x6C is clear. That layer gives it to its Pure3D camera (`0x274750`: projection and frustum) and works out its culling angles from the same fov, so the hook widens the fov (radians, horizontal; 91.3 degrees in play at 16:9, 74.5 in the frontend) and moves the far plane (3000 in play) there, and everything stays consistent. The per-frame entry (`0x1BD100`, USA `0x1BC720`) clears +0x6C when a setting changes, so a still camera updates at once. The level's fog planes (`rm_SetFogPlanes`, layer +0xE4/+0xE8, 50-650 in the tutorial) are scaled around the frame's fog setup (`0x1C2C20`, USA `0x1C2210`) and put back after it. Verified on the European disc on 2026-11-02 with three scripted tutorial runs (default, `fov_increase = 30`, `render_distance = 400`), zero logged errors each: +30 shows a visibly wider view with an unchanged HUD; 400% fog makes distant canyon walls and structures clearer and also reveals a bright sky glow (with a purple edge) that the fog normally hides. The menu rows were seen rendering in the pause menu, and changes made there applied immediately and were saved. The USA functions match the European ones instruction for instruction but have not been run.
- Language (`src/common/language.cpp`, row 8 of Display Options, `settings.toml` `language`; issue #6). The game asks XGetLanguage (`0x20AA00`, USA `0x209F50`) once at boot and maps the XC value to its own (`0xB5296`: English, French 4, Spanish 5, Italian 6, UK English on PAL); the SDK console always said English, so the hook returns the setting. Verified on the European disc on 2026-11-03: French, Spanish and Italian each showed their own main menu text, with the keyboard prompts in that language and no logged errors. French loaded `sound_fr.rcf`, Italian `sound_it.rcf`, Spanish `sound_en.rcf` (the disc has no Spanish voices). German is not in the game's table and was left out. Not run on the USA disc.
- Camera Distance (`src/common/view.cpp`, the mouse wheel in play (no menu row), `settings.toml` `camera_distance`; issue #4). The chase camera (vtable `0x406130`) eases its distance (+0x444) toward a base distance (+0x440, `cm_SetChaseCamBaseDist`); its update (`0xA76A0`, USA `0xA75D0`) is wrapped to scale that base and put it back after. Verified on the European disc on 2026-11-03: tutorial runs at 50%, 100% and 200% showed Hulk visibly closer and farther, with no logged errors; three posted wheel-up messages in play moved 100% to 70% and saved it. The tighter follow and less swing that issue #4 also asks for are not done. The USA hooks are matched by instruction pattern and have not been run.
- Direct3D 11 renderer (`patches/zzzz-d3d11-renderer.patch`: `sdk/runtime/gpu/d3d11.cpp`, renderer choice in `sdk/runtime/xdk/d3d8.cpp`, `d3d12.dll` delay loaded; issue #5). It follows `d3d12.cpp` step for step with the same HLSL (shader model 5, or 4 below feature level 11_0): pipeline state objects become input layout, shader and state objects; uploads go through dynamic rings; rect clears of depth and stencil are drawn; late read-backs use staging textures with event queries; renderer extensions are not supported. `d3d8.cpp` makes the Direct3D 12 renderer unless `XBE_RENDERER=d3d11` (`settings.toml` `renderer = "d3d11"`) or `d3d12.dll` cannot load, and makes the Direct3D 11 one when 12 fails to start. Verified on 2026-11-03 on this PC (Intel UHD Graphics, feature level 11_1) with Direct3D 11 forced: the intro movies, title, tutorial gameplay with HUD, subtitles, fog and bloom, and the pause menu over its blurred scene all drew like the Direct3D 12 captures, with no logged errors; median 59.9 fps against 41.9 on a Direct3D 12 run of the same replay (single runs). `renderer = "auto"` still picks Direct3D 12 here. The import table lists `d3d12.dll` as delay loaded. Not tested: a real graphics card or driver without Direct3D 12 (the automatic fallback itself), feature level 10 hardware, Windows 7/8 (the executable also needs `d3dcompiler_47.dll`, which Windows 7 lacks), the USA disc on Direct3D 11.
- Mods (`src/common/mods.cpp`, `src/common/rcf.cpp`, `tools/modtool.cpp`). `GameInfo::file` now goes through `ModFileView`, which stacks changes on what the game reads: a whole-file replacement from `mods\<mod>\<disc path>`, then the archive's files that mods replace (the cement directory entry points at the mod file's bytes past the archive's end, read from the host file on demand), then the Display Options edits of `misc.rcf` on top. The archive name hash is not known, so files can be replaced but not added. Verified on the European disc on 2026-11-02: a test mod replacing `frontend\lang\str_en.txt` and `str_uk.txt` showed its text on the title screen ("MODDED - Press START") and the Story Mode menu ("MODS WORK"), with the keyboard prompts and Display Options edits still applied, and no logged errors. A second test replaced two `art.rcf` copyright models: the log shows both repointed and the game ran normally, but that screen did not appear in the boot captures, so the swap was not seen on screen. `Hulk Mod Tool.exe` extracted all 17,415 archive files (2.8 GB) from the extracted game in about 7 minutes; reading from a disc image uses the SDK's `Disc` class and has not been run. The USA build compiles with the same code but was not run with mods.
- Keyboard input maps to controller port 1 and clears held keys on focus loss (`tests/keyboard.cpp`). Optional controller replay is enabled only through `HULK_TEST_INPUT` for smoke tests (`src/common/replay.cpp`, `tools/Send-TestInput.ps1`).
- Cursor visibility when gamepad is detected (src/common/keyboard.cpp, src/common/game_info.cpp, tests/keyboard.cpp; issue #7): the mouse cursor was previously visible in menus and tutorials for mouse navigation even when playing with a gamepad. The cursor is now hidden and mouse menu clicks/wheel events are ignored while a controller is plugged in, keeping the screen clean for gamepad play. Disconnecting the gamepad in a menu immediately restores cursor visibility and mouse navigation.
- Button prompts cover the whole string table: every one of the 27 `\b` codes in `frontend\lang\str_*.txt` is either a mapped button (`ju us at sp ta ru la lr ra se jc uc ac sc` → key or mouse wording, `src/common/display_menu.cpp`) or a map/objective icon that stays an icon (`mt mn mj mh mp mi mg me ms md of ob os`). The title screen's own lines are now worded for the keyboard ("Press Enter", "Press any key", "[Space] Start") instead of "Press START", and `settings.toml`'s `button_prompts` (`auto`, `keyboard`, `controller`) picks whose tooltips the tables carry when a controller and the keyboard are both in use.
- The HUD's mission hints (jump pads, acquire, weaponize, drop) come from the mission scenarios, which name a controller glyph (`\bse`, `\bsp`, `\bus`) that the HUD draws by hashed name, out of reach of the string tables. With the keyboard's prompts the hook on `hud_triggerButtonHintBegin` (`0x000CE870`, USA `0x000CE700`) leaves that name out for the call and the instruction line starts with the key instead ("[Space] Jump to City", "[Q] Drop Item", "[E] Weaponize").
